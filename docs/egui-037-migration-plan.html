1. Decision in one page

CADCraft's committed dependency state does not currently build as written: Cargo.toml:52-57 asks for egui/eframe/egui-wgpu/egui_kittest 0.37 while craft-ui is pinned to 5c874d51…, whose egui dependency is 0.36.2. The lock therefore resolves two incompatible egui families, and DockArea::show receives a 0.37 Ui from a 0.36-typed API. This is a reconciliation task, not a version bump.

Target state:

  1. One immutable egui family from the final reviewed storytold/egui revision. That revision is not known or pinned by this plan; it exists only after the approved publication of the fork's reviewed patch series. The aiongg candidate a4f9a17f64a6bae61350fb85804c9df0d9865916 and upstream 841a328b are comparison inputs, never production pins.
  2. One immutable winit from the final reviewed storytold/winit revision containing the W1-W15 base, W17-W27 language/IME series and the new W15P PRIMARY path. The aiongg candidate 8b35388bd719e8cc86a95971ba0bc026c9a8f058 contains W17-W27 but no PRIMARY and is only a comparison input.
  3. craft-ui and craft-docpath from one final reviewed storytold/craft-libs revision that is current main (49190884…) plus only the egui-API hunks ported from PR #199's 8614e4a…. The PR head b68de8c… and audit tree ec8840a… are stale unsafe trees and are never merged or checked out as the target.
  4. CADCraft source changes limited to: the real compile-error classes (UserData/Event::Screenshot, MouseWheel.source, private FontsView.fonts), the deprecations clippy -D warnings rejects, panel-id/PanelState migration, the strict kittest names/glyphs needed for a green first compatibility PR, and the deliberate lifecycle/screenshot/PRIMARY/IME changes below. There is no update→ui rewrite: eframe::App::ui and a root Ui are already used (apps/cadcraft/src/main.rs:91, crates/ui-egui/src/lib.rs:627).
  5. A lifecycle split that is correct under the actual pinned integration: both native and web call App::logic and App::ui inside every Context::run_ui pass. A completed run_ui leaves current_pass_index() == 0; a logic-only tick also reports zero. Visibility is not a phase. Frame-once work uses the zero-pass-index guard; input-dependent work moves into App::ui; consume-based queues run on every logic callback. This is a correction of an existing 0.36/0.37 hazard, not a new 0.37 lifecycle.
  6. Screenshot completion uses the shared craft-ui CL-2 design: one bounded, cancelable completion slot per admitted request, a callback holding only a weak reference to that slot, capture-time viewport/geometry/DPI binding, and aggregate byte bounds. The callback never holds a strong Context (which would create a Context→command→callback cycle) and never writes files or encodes PNGs.
  7. One atomic compatibility PR (S2), then behaviour PRs as in §12. S2 must already be green under strict kittest accessibility and missing-glyph policy, so it owns the accessible-name and default_fonts/monochrome_emoji_fonts work; S4 then owns the broader language, AccessKit-language and Arabic checks.

3.3 Actual frame lifecycle and the pinned integration

Verified against native crates/eframe/src/native/epi_integration.rs:338-365 and native/run.rs:235-281, web crates/eframe/src/web/app_runner.rs:280-325, and egui context.rs:1099-1158,1190-1218,2124-2129:

  • Both native and web call App::logic and App::ui inside the run_ui closure, once per pass. Native update calls app.logic(ui.ctx(), frame) then app.ui(ui, frame); web does the same. On a second discard pass the same two calls happen again with empty input. This is already true on 0.36.2 (767b1cad has the same order); it is not a 0.37 introduction.
  • A hidden root window runs ctx.run_logic → App::logic only. Native reaches this through PassMode::LogicOnly when a redraw is overdue (native/run.rs:267-281); web through run_logic when the tab viewport is not visible (app_runner.rs:318-328). No egui pass runs, so current_pass_index() stays 0 and input/layout remain from the last pass.
  • current_pass_index() is 0 during pass 1 and during a logic-only call, 1+ during later passes. After a completed run_ui, end_pass takes the viewport output (mem::take), so it is 0 again; do not expect a nonzero index after completion.
  • ViewportInfo::visible() is derived from minimized/occluded (egui/src/data/input/viewport_info.rs:98-104); it is None when either flag is unknown and Some(true) only when both say visible. A compositor can withhold a frame without setting either flag, so a logic-only overdue tick can still see None or Some(true), and a hidden window can still run a full run_ui when a screenshot or RequestPaintWhileHidden asks for pixels (native/wgpu_integration.rs:695-727). Visibility cannot distinguish a logic-only tick from a forced hidden UI pass.
  • App::raw_input_hook is called by prepare_raw_input for both update and update_logic_only (epi_integration.rs:338-344,385-425) and before the visibility branch on web (app_runner.rs:284). It must not assume that a UI pass follows.
  • Context::run_ui re-runs its closure for each pass requested by Context::request_discard (default max_passes = 2). Context::root_ui panics while the root Ui is borrowed (#8535); CADCraft keeps the handed-in &mut Ui.
  • Screenshots are callback based: ViewportCommand::Screenshot(ScreenshotCallback) / Context::request_screenshot (#8489); the callback receives only Arc<ColorImage>, runs at most once, and does not request a repaint.
  • #8748 is a closed, unmerged PR (“run the ui of an overdue window without painting”) and is not in the pinned 0.37 source. The pinned source has PassMode::LogicOnly, not PassMode::Overdue; its body confirms that such a window “only runs App::logic”. Do not use #8748 to justify current behavior.

3.4 UI state, commands, undo and persistence

  • UI state is UiState (lib.rs:70-112) and is persisted by the desktop apps/cadcraft/src/workspace.rs as JSON (docking, panel visibility, theme, language, recent files), version 1, bounded at 64 KiB.
  • persist_egui_memory is false (apps/cadcraft/src/main.rs:107), so eframe does not save egui Memory. The app's own Workspace JSON does not store egui ids or PanelState.

6. Root Ui, multi-pass and logic-only semantics

6.1 Rules

  1. CadApp::ui(&mut self, ui: &mut egui::Ui) remains the only root-Ui entry. Panels are added in the existing order; dialogs/windows/areas continue to use ui.ctx(). No code calls Context::root_ui inside ui (it would panic, #8535).
  2. frame_tick(ctx) := ctx.current_pass_index() == 0. It is true on pass 1 and on every logic-only tick, and false on later passes. It is the only frame-once guard. Do not use cumulative_frame_nr for this: run_logic does not increment it, so a hidden tick and the next full frame share a number and would duplicate work.
  3. Input-dependent work (shortcuts, clipboard mirror, dropped files, canvas zoom from wheel events) runs in App::ui on the first pass, never in App::logic. run_logic leaves events/time stale; reading dropped_files or Event::Paste there replays a user action on every hidden tick.
  4. Consume-based background work runs on every App::logic call: the control mpsc drain, opening-job receiver, screenshot completion receiver, GPU-fault take, and the Plot/Hatch resume flags. These cannot duplicate because each item is consumed once. They must not be hidden behind the pass-index guard, or a fresh control reply, opening result or GPU fault arriving during a later pass would starve until the next frame.
  5. Deadline/time-based work (LISP slice, autosave, queued-screenshot issue, workspace persistence, spacemouse poll, native-menu poll) runs on frame_tick. Autosave and the screenshot queue are additionally idempotent by their own deadlines; the guard keeps pacing deterministic rather than relying on that.
  6. UI is never shown from logic. The opening spinner currently drawn at lib.rs:580 moves into draw() as a foreground Area; opening::show keeps its rendering code but is called from ui.
  7. Per-pass handlers that do run twice must be idempotent by a saved value, a shown_* field or a consumed queue. control::begin_frame still clears the observed-widget list at the start of each UI pass.
  8. Input events are removed only after the app handled them: raw.dropped_files always; Copy/Cut/Paste/MiddleClickPaste only when !ctx.egui_wants_keyboard_input() (the guard menus::shortcuts uses). A focused TextEdit still receives them. Do not clear Text/Key before CadApp::ui because the command line reads them there.

6.2 Split (design, not code)

fn frame_tick(ctx: &egui::Context) -> bool {
    ctx.current_pass_index() == 0   // pass 1 or a logic-only tick; 0 after completion
}

pub fn logic(&mut self, ctx: &egui::Context) {
    // Consume-based: every call, never behind the guard.
    self.drain_control(ctx);
    self.finish_opening();
    self.collect_screenshots(ctx);
    self.gpu_fault_tick(ctx);
    managers::plot_window_resume(self, ctx);
    hatchdlg::resume(self);

    if frame_tick(ctx) {
        // Once per layout frame or hidden tick.
        self.session.lisp_tick();
        if self.session.lisp_busy() { ctx.request_repaint(); }
        self.close_request_frame(ctx);
        self.apply_theme_fonts_zoom(ctx);
        self.issue_screenshots(ctx);
        self.autosave_tick(ctx);
        if !self.synthetic.is_empty() { ctx.request_repaint(); }
    }
}

pub fn ui(&mut self, ui: &mut egui::Ui) {
    let ctx = ui.ctx();
    if frame_tick(ctx) {
        self.ui_input(ctx);       // shortcuts, clipboard mirror, dropped files
        self.frame_wheel(ctx);    // apply fresh wheel/zoom exactly once
        self.frame_cap_wait();    // pacing belongs to a painted pass
    } // later passes draw the already-updated state; never re-inject consumed wheel input
    i18n::with_language(self.language(), || self.draw(ui));
}

ui_input clears raw.dropped_files after opening them, and calls menus::shortcuts (which consumes shortcuts and clipboard events). frame_wheel runs animation::unsmooth_scroll when animations are off and applies the frame's wheel scroll/zoom once. Later passes render the resulting view; they neither re-inject events nor reapply a cached delta in canvas.rs. frame_cap_wait is moved out of raw_input_hook because the hook also runs on logic-only ticks where no paint will happen.

raw_input_hook keeps only work that is safe without a pass: the desktop theme override, cmdline::capture_tab, and synthetic-event injection. Injection drains self.synthetic once into RawInput; eframe preserves that input in pending_raw_input across logic-only ticks, so repeated ticks do not duplicate the same event. Add a test that a queued synthetic event is applied once after a hidden tick followed by a shown frame.

6.4 Screenshot callback correlation and bounds

State per admitted request (owned by CadApp, with paths/replies/deadlines kept in the app):

ShotRequest {
  token: u64, path: Option<String>, reply: Sender<Value>, deadline: f64,
  viewport: ViewportId, session_generation: u64,
  expected_px: (u32, u32), expected_ppp: f32,
  slot: Arc<ShotSlot>,            // one completion slot per request
}
ShotSlot { state: Mutex<ShotState>, wake: egui::Context }
ShotState { canceled: bool, result: Option<Result<Arc<ColorImage>, String>>, bytes: usize }

issue_screenshots waits for canvas.building() and at least three accepted UI frames (an intentional settling unit, never three discarded passes), then calls ctx.request_screenshot with a closure holding Weak<ShotSlot> only:

let slot = Arc::downgrade(&request.slot);
ctx.request_screenshot(move |image: Arc<ColorImage>| {
    if let Some(slot) = slot.upgrade() {
        let wake = slot.complete(image); // stores image/result, releases the lock
        if let Some(ctx) = wake { ctx.request_repaint(); } // Context lives in the slot
    }
});

The callback must not capture a Context strongly: the callback is itself stored in that context's viewport commands, so a strong Context would form a cycle. It must not encode PNGs, write files, run commands, or hold a lock while waking.

collect_screenshots drains the slot results on every logic call, checks the token and request/session binding, and replies with save_screenshot(&image, path). Binding:

  • CADCraft has ROOT only: bind to an explicit CadApp session/document generation. The callback supplies pixels only; viewport identity is request-owned, not callback metadata. Reject generation changes/close and never reuse an old result for a new document;
  • At issuance refresh expected geometry from the target UI content rect and ppp, after the settling wait. If no fresh UI geometry exists, request a paint before issue. Revalidate a monotonic resize/DPI/zoom/surface epoch before saving; derive scale from returned pixels and unchanged logical bounds, including E2 fitting. A mismatch is: reply {"ok":false,"error":"window geometry changed during capture"} and release the image rather than silently pairing it with a newer request;
  • a late callback whose slot is canceled or dropped releases the image without a file or reply; a timed-out request leaves no file and cannot later write one;
  • admission limits: at most 4 pending/queued requests and at most 64 MiB aggregate reserved in-flight plus completed image bytes (64 MiB per-image maximum as well). Reserve checked expected width×height×4 bytes at admission, adjust before issue after a geometry change only if capacity permits, otherwise reject. Requests over the limit are rejected immediately with an error reply. pending_bytes is decremented on drain, timeout, cancellation and dropped slots;
  • cancel all slots on close/viewport loss and in on_exit; cancellation is a flag, not a process kill. now_ms is 0 on wasm, so the deadline uses web_time::Instant on web, never stale InputState::time; do not leave an infinite web deadline.

CADCraft adopts the shared craft-ui CL-2 completion-slot API (the eleven existing craft-ui creative consumers' approach; DeckCraft, FigCraft and ArtCraft Native keep local adapters). Request records, paths, PNG serialization, timeouts and the reply schema stay in CADCraft. If the provisional CL-2 API is unavailable, S3 is blocked rather than growing a second divergent helper.

Regression assertions:

  • two requests in one frame, distinct paths, both files have the harness's pixel size and each reply names its own path;
  • a request while a popup forces a second pass produces exactly one file;
  • a timed-out request leaves no file and cannot later write one;
  • a minimized/hidden window reports the documented timeout, or succeeds through a forced hidden paint (RequestPaintWhileHidden/screenshot), never hangs;
  • admission overflow returns an error and does not grow memory;
  • a completion after resize/DPI change returns the geometry-mismatch error;
  • a late callback after close writes nothing.

kittest fulfils ViewportCommand::Screenshot in Harness::handle_screenshots (0.37 egui_kittest/src/lib.rs:909-947), so routing/bounds are testable without a real window.
